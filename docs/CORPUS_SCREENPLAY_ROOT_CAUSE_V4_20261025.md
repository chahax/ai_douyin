# 自动剧本返修原因与修复（2026-10-25）

用户要求“找原因接着改”，范围是自动流程，不能由助手改正文冒充模型成功。当前代码回归通过，真实原生稿仍未验收通过。

## 找到的原因

1. **失败全文成为编剧模板。** v3 虽有来源事实表与全片重排要求，MiniMax 仍保留旧段落秒数，仅局部替换对白；返修把家中结尾从6秒压到5秒。新增拦人内容又挤入原7秒段。
2. **审核判定缺少独立数字约束。** 两次全文审核会共同漏看结尾，或漏读已有拦人动作，反而要求补戏；裁决也不能保证纠正这类漏读。此前每秒6单位只筛极端不可能情况，不代表自然语速可行。
3. **引用协议导致非内容阻塞。** 事实整理引用了正确原句但错章；审查省略 Markdown 加粗或跨段引用，被连续字符串匹配拒绝。后续时长报告又漏字段、改写引文，消耗调用但没有改善正文。
4. **新写也会产生独立事实错误。** v4 首次彻底移除失败稿后，仍出现“老大11岁、老二12岁”、钱先在手中后从口袋取出，以及处理叶东事件时无由询问西决。新写不等于质量已合格。

## 最终实现

- 当前全可读小说入口、`run_fanqie_corpus_workflow.py`、`run_corpus_screenplay.py` 的新计划使用 v4。冻结的 v1/v2/v3 继续按各自版本处理，不能把旧审核改成通过。
- 原文与来源 SHA 绑定事实表，原句只在本次冻结章节内唯一匹配时更正章号，并单列证据；不改事实正文或原响应。
- 首次重建仅给原文、事实表及创作要求，不给失败全文和候选结尾。完整原稿仍存档。
- 引用校验只去除 Markdown 标题/加粗及空白；多段引用逐行顺序定位，每行都要逐字存在，拒绝改字和省略号拼凑。原审核不覆盖。
- **编剧后立即逐段预检**：识别连续秒数段，保守计入段内所有引号内容（包括行内对白）；对白按每秒5语音单位已经超时，先自动退回完整返修，不先花审核调用。连续两稿仍超时停止。数字不证明语气或动作可演完。
- 通过预检后做全文审核和独立动作时长审核。程序计算对白加串行动作，再与并行动作时长比较；审核口头 pass 不能覆盖计算出的超时。
- 动作审核使用程序分配的原文段落 ID，减少模型重复抄写动作时改字导致的协议失败。无法定位、漏段、重复引用、无效时间均拒绝。
- 每份返修要求与稿件 SHA 单独留档；原人物、道具、语义、动作及信息推进仍需模型完整审核。没有将关键词匹配当语义通过。
- 预算转移一次登记，父任务封住，子任务绑定父状态和原计划；原消耗累计，未知请求不重新派发。

## 实际验证与边界

最终 **70个用例通过**，JUnit：`data/qa/v4_acceptance_final.xml`。覆盖来源/稿件变更、错误引用、时长遗漏/超载、失败稿不作为首稿模板、预检在审核前返修、完整返修与再次审核、未知不重放、预算一次转移及全可读工作流接线。跨故事检查为离线测试，不能当不同故事真实模型质量通过。

真实 v3：18次调用、365177 reported tokens，2次完整自动返修后仍存在超时；最终裁决 checks 与 issues 不一致，停为已知验证失败，pending=null。

真实 v4：从 v3 转入剩余5次/134823 tokens，复用同源事实表。MiniMax 原生新写一次，DeepSeek 全文审核一次，时长审核及协议返修各一次，共4次/88703 tokens。最终时长动作引文被改字，未通过证据校验；正文审核本身也是 revise。没有交付通过稿。

本轮 v3+v4 共 **22次/453880 reported tokens**，继承后 **51次/1173516**。原范围剩余1次/46120 tokens，无法完成新一对创作及审查，本轮没有再派单独无法验收的新稿。已收到结果全部保存，不是超时未知。
