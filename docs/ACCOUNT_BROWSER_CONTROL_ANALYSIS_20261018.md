# 账号浏览器管控：现状分析与待确认方案

状态：analysis_complete_awaiting_user_confirmation。2026-10-18用户要求先分析功能模块、询问后再开发。本轮仅静态阅读与方案记录，未改生产代码、数据库、运行锁或服务，未重启浏览器、上传、发布或评论。

## 目标及归属

用户希望复用自动化窗口中的登录会话和标签页，以完成已授权视频发布；并明确该能力属于管控模块。

建议由`operations_accounts`提供统一的账号浏览器管控入口：决定谁拥有浏览器、任务何时运行、用哪个标签页、何时等待人工与如何恢复。发布模块只处理发布表单、平台AI声明、提交及作品核验；后台调度只提交到期任务，不自行争抢浏览器。不是在上传脚本里单独开一个标签页。

## 已核对的实际职责与缺口

| 模块 | 当前职责与实际实现 | 本次相关缺口 |
|---|---|---|
| `operations_accounts/runtime.py`、`repository.py` | 账号/真实身份/profile绑定，operation_lease、配额、熔断和锁归属 | 资源所有权与一次业务执行共用运行锁，尚无独立浏览器会话管理和借用协议 |
| `scheduler/account_refresh.py`、`account_playback.py`、`account_manual_windows.py` | 到期任务、持久暂停、恢复探测、异常自动开窗去重 | 调度与人工窗口可互斥，但不能把新发布请求交给已持有浏览器的原worker |
| `operations_accounts/maintenance.py` | 一轮内核验身份、采集、播放/回接，保存状态并关闭会话 | **已有轮内复用**：identity_session传给研究和播放；尚非跨任务复用，不能说全项目都没有复用 |
| `manual_handling.py`、`manual_window_jobs.py` | 原账号可见窗口、异常关联、人工处理、运行锁及关闭回执 | 持有manual-session直到关窗；尚无“保留窗口并完成处理/交还控制”的入口 |
| `platform_adapter/browser_session.py` | 每个BrowserSession启动独立子进程及persistent context，通过stdin/stdout串行命令操作 | worker只保存一个当前page；无按任务绑定的tab registry；wait_for_close长时间占住命令循环与RPC，不再读取新命令 |
| `DouyinAdapter`、`PublishWorkflow`、`creative_delivery` | 绑定账号和成片，上传、标题/标签、主动AI声明、虚构前缀、唯一提交及原作品核验 | 新建adapter通常新建BrowserSession；缺少向既有会话提交任务的公共入口。应保留现有声明与防重复提交门 |
| `web/account_refresh_dashboard.py`、`publish_run_dashboard.py` | 显示各自后台/发布状态和处理入口 | 缺少统一的“当前账号浏览器、正在执行、等待人工、排队发布”视图 |

另查`scripts/creative_workbench.py`与adapter中的发布路径：直接创建账号adapter并调用发布，没有在这些路径看到统一的operation_lease包装。不能因身份核验存在就认定已统一接入调度互斥；开发时需逐入口补齐，而不是只改一条上传路径。这是本次所查路径的结论，并非已完成整个项目所有调用点的审计。

实施前主审补充纠正：最初只读`auto_publish_service._publish_video`时将它也归为“无lease”范围过大；完整`publish`函数上游实际有acquire_runtime，但先核验身份后申请锁，仍可能提前启动独立浏览器。该旧一键创作路线已停用，管控接入应保持停用，并导向已批准完整片的持久发布入口，不因本次重构复活旧生成流程。

`manual_window_jobs._orphaned`按调用进程PID/nonce判断任务登记。因此独立CLI读取另一个仍存活服务持有的job会投影outcome_unknown。前次本地核对已见原数据库running/window_open_waiting_close、owner PID仍存在；该投影不能单独证明原worker死亡。未来管控必须区分跨进程只读状态与真实持有者失联，PID存活本身也不能代替会话健康。

## 建议结构

```text
网页 / CLI / 后台到期任务
          ↓ 账号、任务和明确授权绑定
账号浏览器管控（operations_accounts）
  统一排队、业务暂停门、资源所有权、身份核验、状态与恢复
          ↓ 单账号单worker，业务操作串行
BrowserSession：同一context中的受管标签页
  人工处理页 / 研究播放页 / 发布页 / 对应作品页
          ↓
现有采集、播放、发布、声明和核验模块
```

同一账号共享原登录context，但不同任务持有各自tab handle，不能把全局page切来切去。不同账号仍隔离。多标签不等于允许多个任务同时操作同一账号；尤其不能由一个任务关闭其他任务的浏览器。

## 管控行为建议

1. 区分浏览器资源归属与一次业务执行：资源owner负责单实例和profile，操作owner负责串行执行、原配额与熔断。窗口闲置可保留，但不再以“等待关窗”的业务锁阻止新请求。不能简单删除当前锁或让发布绕过锁。
2. 人工处理改为可查询的状态，不用一次阻塞RPC守到关窗。保留原验证页，用户完成处理后在管控页面点击“处理完成”；原worker在同一会话复核绑定身份与阻断状态，再决定是否执行排队任务。可关闭窗口，但关窗不再是唯一交还方式。
3. 验证未完成或账号处于安全阻断时，发布等业务继续排队。复用标签页不等于验证码已通过，不自动代做验证码、不把探测成功写成实际播放/发布成功。
4. 发布请求优先级待用户确认：推荐当前播放项/采集步骤在已验证可恢复的边界结束后，让位给显式发布；发布及核验结束后按保存进度恢复原任务。没有可靠恢复点的旧任务先等整轮结束，不能伪造恢复能力；未取得原结果的发布点击不可中断重派。
5. 所有入口通过同一管控服务提交可追溯命令，使用原账号UUID、绑定版本、任务ID、会话代次与幂等键；不能只在某网页里保存一个内存浏览器对象。旧任务仍按原身份和锁对账，新功能不清理旧未知任务。
6. 会话生命周期按需启动、空闲回收。正常后台仍静默/静音，已有可见窗口可保留复用。现有headless参数在启动时固定，**不承诺给正在运行的无头进程直接显示窗口**；需要切换时在可证明空闲后重建同一profile的会话，记录新的会话代次。前端文案区分“复用登录环境”与“同一进程未重启”。
7. 保留两类不同恢复：业务暂停后恢复原任务；浏览器owner丢失后核对原外部结果。未知上传/发布/评论不自动重发，提交锁、原作品ID及原生回执始终保留。浏览器复用本身不扩大内容或发布授权。

## 开发分工（用户确认后）

先做只读现状与数据库/代码检查点，不覆盖旧媒体、冻结记录或凭据。再由子agent按边界实现，主agent审查实际接线：

- 管控核心：持久任务与会话状态、串行准入、owner代次、身份/暂停门、优先级和未知恢复。
- 浏览器执行器：tab handle、会话借用、短命令/状态轮询、关闭归属及状态保存；不承担发布业务规则。
- 入口接线与界面：后台、人工处理、发布/核验/已授权评论统一走管控；页面展示运行、排队、等待人工及原任务。
- 主agent核验跨模块行为、原声明与提交锁、配额不重置、旧调用路径不绕过，并审查可部署条件。

先离线与本地空白页实测，再在没有在途账号操作时部署。当前正在运行的旧worker没有新协议，不能仅改文件就宣称已接管原窗口；首次迁移需原任务正常交还或在可核对的停点结束。部署时机与原窗口实际状态另核对，不能擅自中断。

## 验收应证明的结果

- 同一账号的第二个任务复用同一受管context，保留原标签页；跨账号不串会话。
- 人工页保持打开时能够提交、查看排队任务；等待状态不堵worker命令处理。
- 人工处理完成后同会话核验身份，未通过不能发布；原暂停/失败不被窗口操作清零。
- 后台让位/恢复的真实进度有保存证据，不能只验证任务状态字符串。
- 网页、CLI、后台同时提交不会开两个profile实例、争抢page或重复发布；旧任务仍可只读核对。
- 进程退出/心跳过期/迟到响应/数据库忙/新代次拒绝旧命令；跨进程查询不误判为原worker死亡。
- 上传始终使用已批准完整片；“内容由AI生成”选中与提交前读回、虚构前缀/标签、唯一发布与对应作品核验全部保留。
- 评论单独绑定准确作品与本次授权，保存发送/读回；结果未知不重复评论。
- 空闲回收不关掉仍供人工处理的页面，不以关闭一个任务标签页等同整个账号退出。
