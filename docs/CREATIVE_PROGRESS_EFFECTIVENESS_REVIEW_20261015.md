# 错误复盘、实际进展与后续时间估计

日期：2026-10-15。本次为只读生产证据复盘及文档整理，没有新增模型、媒体或发布请求。

## 结论

有逐次不可变调用回执，也有多份分轮修复与结果文档，但**没有做到每次错误都形成经生产验证的根因与修复闭环**。部分记录是故障现象或待验证解释，不能因另一个合同通过就认定原问题已解决。

也不能说每次都更接近最终目标。第601次调用后，第602–619次共18次调用，926,348 reported tokens；涉及5份整片规划、2份初态及11份审查，没有新增完整正文，更没有本轮导演、逐镜表演或制作交接。这一段的交付进展明显不足。

619次是项目历史累计，不能全部归因于这18次或本次超市故事的审查修复。

## 哪些总结有用，哪些地方没有闭环

确有实际增益：接收协议区分完整失败与未知结果；缩减巨大strict请求后能获得完整报告；固定法律依据从自由改写改为精确原文绑定。原始证据、失败与消耗保留，没有为过门篡改正文或回执。

不足在于：

1. 引用枚举、引文保真和目录覆盖反复失败，修复常针对当次字段形态，没有证明同类问题已稳定解决。
2. 同一个审查输出同时承担法律命题识别、实际条件判断、来源映射、精确引文和全目录覆盖。最近结果表明这种分工尚不稳定，继续增加说明和Schema不能自证有效。
3. 结构通过曾掩盖语义漏审；增强敏感度后又出现把普通叙事事实推为法律效果的现象。审查需要同时测漏报和误报。
4. 来源审查失败时多次连带重生成完整规划，未始终把审查缺陷与故事本身的缺陷隔离。
5. 离线测试大多证明协议、守卫及故障分支，不能回答对白是否自然、冲突是否增强、故事是否更可制作。最终评价重心偏离了实际作品交付。

这些是根据当前证据作出的工程诊断；MiniMax旧长分析的服务端内部原因、strict嵌套约束失败的服务端内部原因仍未知。

## 后续如何判定真正靠近目标

先保留并尽可能复用完整原生规划618，定位审查分类缺陷；只有确认规划本身需要改变时才生成完整新规划。固定故事方向、固定法律来源与真实问题样本，避免输入和规则同时变化后无法归因。

让程序承担可确定的目录、身份、类型与覆盖校验；模型承担文本中实际表达了什么、是否构成法律主张和叙事质量判断。程序不能替模型补造缺失判定，也不能放行漏审的原报告。

下一轮必须同时验证：双签/空栏等实质法律前提不漏审，人物请求/排班等叙事事实不被自动当成法律结论，精确引用与目录覆盖有效，随后真正生成完整正文并完成同稿全文审查。只得到另一个有效规划或另一批离线通过，判为尚未取得交付进展。

如果同类关口再次失败或仍无正文，应停止沿当前方案增加规则，明确评估职责拆分或审查接口路线；不把“继续多试几次”当作策略。本记录不新增调用范围、重试额度或自动重新派发授权。

## 时间估计与不确定性

这是工程估计，不是已有验证支持的完成保证：修正当前审查关口并完成下一轮正文验证，可先按2–4小时估计。若关口通过，单个故事走完正文、导演、表演与文本制作交接，暂按半天至一天估计；不含视频生成与用户审片。

可复用、脱离逐稿人工挑错的稳定流程，还需要在不同主题/关系/情绪目标下复现。现在没有足够成功证据给它承诺可靠完成日期。应先验证一份完整交付，再根据复现结果修正估计。

不应继续以无限修补消耗时间。下一轮的核对依据是完整正文及同稿审查，而不是测试数量或版本号；若未达到，直接报告失败与路线判断。
