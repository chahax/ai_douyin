# 导演稿分阶段验收

用户验收条件：流程连续3次获得实际读稿认可。此次范围是文本，不生成视频。

2026-09-17已完成：同一最终协议下，trial036、trial037、trial038三份不同剧本完整文本终审连续通过。见[验收报告与三稿入口](../data/director_workbench/three_pass_suite_20260917/ACCEPTANCE_REPORT.md)。这是修订后的三稿回归验收，不是未经干预的三次新生成成功率。

## 固定流程

1. 核验既有20条来源，提取表达机制；旧稿的具体选题不作为新稿的强制剧情。
2. 按内容生成4至6事件提纲，24—45秒，实际检查因果、人物目的、情绪触发和核心动作可行性。短对话优先24—30秒，不为凑45秒填长停顿。
3. 提纲通过后分前后两组生成动作对白，前组实际审读后再展开后组。提纲不是逐字拍摄锁稿；已记录的泛化措辞在动作阶段按初态澄清，不能改变核心事件。道具转移与设施状态只能从真实旧值推进。
4. 动作对白通过后增加摄影；本轮固定同侧全身双人主镜头。模型只选择静态枚举槽位，程序展开为唯一共用构图和光线，不能用自由摄影文字增加动作、台词或物件。只有原scene有顶灯才能选顶灯；逐段focus仅为审稿注释，不进入执行提示词。
5. 确定性导出导演卡、ComfyUI工作流和可读稿，复核最终组合内容。

对白只有 `lines` 一份原文，音轨时间描述由它派生；首末态由动作转移演算，不让模型另写两套库存。程序校验不代替语义审查：例如“晾衣绳挪半寸就不滴水”即使JSON合法仍必须否决。

不同人物的反应允许同时发生；同一人的冲突动作不允许重叠，改变库存和设施状态的动作必须串行。无移动道具的稿件允许空位置清单，不强行添加左右手持物记录。导出每条动作时明确执行人，最终提交文本验收前重新编译比对提示词，防止转换丢失主语或内容。

动作之间默认保持上一个姿态和物件状态，不把正在说话/聆听的静止时段当成缺动作。真实超速句可通过 `speech_window_fit/v1` 重新分配发言窗口并同步映射纯反应时间；不修改任何对白、动作描述或状态，不允许压缩/移动状态改变动作。空间不够则退回编剧，不能把整句加速塞入。原始 `model_output.json`、`raw.txt` 与派生 `candidate.json` 分开留存，审核和终审均重放该转换。

最终镜头提示词的表演来源是已审 `actions` 加事件的情绪触发/变化。作者的自由 `emotion` 注释保留作审稿材料，不作为第二套可执行动作或发声指令；例如注释的“话到一半收回”不能截断 `lines` 中的完整台词。抽帧/音画检查仍须在实际视频生成后另做。

摄影输入也剔除早期提纲的动作描述和作者自由emotion注释，只提供场景、人物、初态、时长、最终动作对白及演算状态。否则模型会在摄影或观察重点中捡回动作稿已删掉的转身、让路等旧指令。

## 认可标准

- 因果：新信息确实支持人物改变判断；结果由已写动作完成。
- 情绪：有欲望、阻碍、触发及可见反应，变化不是只换形容词；对白有潜台词。
- 动作：物理成立、角色能完成；双手占用、持物和设施状态可逐步重放。
- 对白：谁说、说什么、何时说只有一套；不抢话、不额外配音，不靠拖腔填时长。
- 连续性：相邻初末态承接，道具不消失、不凭空出现；摄影不偷偷改变人物位置。
- 可拍性：关键动作和反应可见，构图与光线有意图，时长足够且无无意义空等。

每次认可绑定实际模型原文与候选哈希，记录具体镜号、发现和未解决项。提纲阶段的通过只允许展开动作，不等于全稿通过。没有视频时不作声画或观感通过结论。

## 连续计数

测试用不同创作简报生成独立新稿，不重复审批同一份候选。任何结构或实际读稿失败都中断连续计数。修改流程代码或提示词将改变协议指纹，同一指纹下必须重新累积连续3次完整通过。失败文件和原始调用保留，不删除后重算。

修改测试器或摄影约束后，可通过 `adopt_outline` 对同一套生成提示词下的原始提纲做新协议复验：原模型请求、响应、原文及候选逐字保留并绑定来源，不再调用提纲模型。已完成动作对白也可保留原始响应、重放时间投影后重新审查；缺失或失败阶段重新生成。复验复制不计新增模型调用，不把一份稿件计成多个通过。记录中的连续通过是最终同一协议下三份不同稿件的完整文本验收，不宣称三次模型首发全对，也不是三次从零随机抽样成功率。首批目标是三种关系的独立短场景，范围为双人同场、无持物交接、无手部接触；不是复杂动作戏的验收。

本次模型调用使用本项目已配置的MiniMax服务，并对真实响应保留usage、finish_reason和模型标识；不读取或展示隐藏推理。参数能力核对依据为[官方OpenAI兼容接口文档](https://platform.minimax.io/docs/api-reference/text-openai-api)。

早期adaptive调用出现长时间等待、截断和超时；最终编排使用MiniMax-M3的disabled模式，逐次请求与回执仍保留。原先生成的三份不同提纲和部分动作稿在新协议重放复验，因此它们的历史生成参数如实保留，并未伪装成新参数下的从零生成。
