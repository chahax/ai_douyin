# 管理页交互与状态规范

版本：2026-11-04；范围：管理后台所有导航页、新功能和改动。这里是项目验收规则，不是“已通过 WCAG 合规认证”的声明。

## 依据与适用边界

- W3C WCAG 2.2 [3.3.1 错误识别](https://www.w3.org/WAI/WCAG22/Understanding/error-identification)：错误应有可理解的文字描述；原条款针对输入错误，本项目将相同原则扩展到后台任务异常。
- W3C WCAG 2.2 [4.1.3 状态消息](https://www.w3.org/WAI/WCAG22/Understanding/status-messages)：进度和结果应通过可被辅助技术识别的消息提供，不依赖颜色、图标或焦点跳转。本项目仍需实测 Streamlit 组件与读屏支持，不能仅凭使用 st.info/st.warning 声称达标。
- 异步任务的证据、幂等、原身份及外部副作用规则是项目工程约束，不能冒称来自 WCAG。

## 页面必须回答的五个问题

1. 正在查看哪个账号、批次或作品？执行前展示对象，切换账号不可继承别人的表单和结果。
2. 当前处在哪一步？区分排队、执行、等待人工、结果未知、成功、失败、暂停。
3. 这个状态是哪条记录、什么时间确认的？普通视图显示更新时间，任务编号与诊断进入详情。
4. 用户下一步能做什么？每个对象保持明确的主要操作；按钮禁用时旁边解释原因和解决路径。
5. 点击后发生了什么？登记成功只表示已受理，接着显示原请求进度；有真实终态证据才显示成功。

## 统一状态词汇

| 状态 | 页面含义 | 禁止推断 |
| --- | --- | --- |
| 未配置 / 未绑定 | 缺少必要设置或原身份绑定 | 账号失效 |
| 等待到期 | 有效计划正在等待触发 | 正在执行 |
| 已排队 | 请求已持久化，尚未收到执行确认 | 浏览器已打开 / 视频已播放 |
| 执行中 | 原任务已进入执行，展示实际阶段和最近进度 | 服务在线等于业务成功 |
| 待人工处理 | 有明确阻塞，展示已证实原因及处理入口 | 所有加载失败都是验证码 |
| 正在核验 | 用户确认已受理，原身份或准确作品仍待核验 | 已恢复 / 已发布 |
| 已暂停 | 后续计划被暂停，说明原因与影响范围 | 在途任务已经停止 |
| 状态无法确认 | 读取失败、归属不符、未来时间或过期证据 | 无异常 / 原进程已退出 |
| 已完成 | 当前原任务存在一致的终态回执 | 技术生成完成等于内容审核通过 |
| 失败 / 受阻 | 有原任务失败证据，展示真实原因 | 可以直接重传或重派 |

服务、账号控制、身份绑定、人工窗口、业务任务、成果审核必须分别记录。允许出现“此前播放完成，但后来研究失败导致账号暂停”，不能用一个绿色“登录健康”覆盖这些事实。

## 新鲜度与证据优先级

- 终态回执与其绑定成果优先于同一原ID的中间游标；不能用滞后的12条覆盖终态13条。
- 原ID、账号、身份绑定、owner和代次必须一致。只读轮询不进行接管、清锁、重派、关窗或恢复。
- 人工窗口服务心跳以原控制存储的 owner_ttl（当前90秒）判断。过期只说明无法确认服务，不能证明进程不存在或窗口已关闭。
- 原窗口任务 running/waiting_human 只有在原owner归属与新鲜度成立时，才可展示可处理/可重新显示；否则说明“原窗口服务无法确认”，阻止继续和重复开窗。
- 页面探测与owner心跳分别计算；原页面探测超过180秒时展示过期，不展示“当前没有验证码”。新的身份核验仍须读取实际页面。
- 没有读取到状态时保留“未知”；不填0冒充真实播放计数，不将暂无异常记录展示为运行正常。
- 时间统一展示北京时间完整日期时间。历史核验必须标“此前”，不能遮盖之后的新异常。

## 人工处理与异常卡片

- 历史异常描述、最新窗口状态、账号控制状态分开；禁止把旧回执改写成当前网页要求。
- 同一账号多个异常保留各自编号与关闭记录，开窗和完成操作共用一组；关闭提示只关闭该条，不能解除账号暂停。
- 验证内容未确认、网络/导航超时、后台服务失联、真实验证控件出现必须区分，不统一要求验证码。
- 受管窗口已就绪时可保持打开并申请核验；未确认开窗、失联或结果未知时，不要求用户反复关闭/打开/点击完成。
- 展示阻塞原因、更新时间和解决路径。诊断“需要后台核对原会话”不能伪装成普通用户点完成即可修复。
- 普通用户不应面对多个重复的灰按钮却没有说明；权限不足明确标只读。

## 操作与反馈

- 纯查看、刷新、展开、换页、自动轮询不得新增模型调用、发布、互动、媒体生成或调度任务。
- 所有写操作验证权限、对象、当前状态；防双击、防多会话重复提交，复用原请求；按钮禁用只是提示，后端仍是最终裁定者。
- 点击受理后给出原请求编号和阶段；失败说明是否已登记、有无外部动作、下一步，不直接泄露原始异常栈或凭据。
- 成功结果从持久回执读取，刷新和重连后仍一致；旧成功不得盖过后续新异常。
- 发布/提交未知保留原ID与锁，先核验准确作品；不因界面超时重传。付费生成、互动、删除等动作必须有明确范围。
- 内容由用户审片。验收不自动播放、听音、抽帧或ASR。

## 布局与可访问性

- 页面顶部：标题、范围、总体状态与数据更新时间；随后主要操作、进度、结果；原始诊断置于折叠详情。
- 表单字段有可读标签；必填、限制、错误靠近字段；不依赖颜色表达状态。
- 键盘可访问、按钮有清晰名字；刷新不抢焦点、不清空用户编辑、不反复弹窗。
- 桌面与窄屏检查截断、溢出、滚动、下拉选择和模态层。空数据、长文案、多异常与读取失败必须可用。
- 使用共享状态映射和组件，避免不同页同码不同义；不能为了统一样式去修改冻结生产PLAN或原始回执。

## 黑盒验收和放行

每项功能记录：页面/角色、账号范围、前置状态、输入、点击、可见输出、原请求/回执、外部副作用、结果、源码SHA。

必须覆盖正常、空数据、未配置、权限不足、重复点击、切换账号、读取失败、过期/未知、重连、后台重启和已有运行占用。

验收分层且分别记账：

1. 真实页面只读：导航、范围、展开、筛选、日志和状态，核对DB/原ID证据。
2. 隔离黑盒：真实Streamlit/AppTest控件、临时SQLite/成果目录和受控服务边界，验证有副作用功能及错误分支。不能称作线上外部闭环。
3. 授权生产闭环：用户最终确认具体操作后观察原请求到真实终态。已有真实回执可以做只读比对，不能冒称本轮重新执行。

不得因为本地回归通过就写“全部功能没有bug”。只有清单中每项有覆盖证据或明确限制、当前确认缺陷已修复回归、部署与真实页面核验完成，才交付统一验收。未知与未测保留在报告中，不写成通过。
