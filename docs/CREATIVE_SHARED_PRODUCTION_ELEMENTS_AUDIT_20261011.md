## 结论

上一轮实际修复了闭合人数、机位来源以及模型复制机械身份字段的问题，没有建立完整的全片人物身份合同。三段都沿用同一个487源稿，但“同稿”“同名”“共两人”“传入正确原尾帧”不能证明画中人物与逻辑角色保持一一对应。此次用户的画面拒绝不推翻原接口保存成功；它证明了真实人物连续性未通过。

### 已核实的缺口

1. `scene_and_character_context.characters`在开场、第二段和第三段均只有id、name、role。没有结构化的性别、年龄感、发型五官、确定服装、声线或具体角色参考绑定。正文FULL_SCRIPT也仅有title、premise、beats和selected_candidate_id，角色职责在独立简报里。
2. `actor_id → 显示名 → 原对白`有映射；`actor_id → 原始参考中的具体人物 → 外貌/声音`没有映射。编译器验证名单与全稿说话人一致，却无法确定图里的谁是小林、谁是周姐。
3. 最新实际视频prompt明确写“周姐、小林，共2人”及同衣服、工牌、座位，但没有明确人物形象档案。完整人物/场景context虽然进入MiniMax和DeepSeek输入，也保存在PLAN中，视频API实际只收到text及image_url，并未直接接收这些归档JSON字段。
4. 开场用旧SH01原产物一张reference_image；第二段用开场原尾帧；第三段用批准第二段原尾帧。最新request与REQUEST.preview完全相等，唯一first_frame解码SHA为a980fb18daa9d8f421102f0e989d05ba1de10e7cb2c92b326c7a1c1e4a9c07bc，精确对应批准second_v4。没有漏传/错用尾帧的证据，但人物身份主要由这张图隐含承担。
5. `generate_audio=true`及普通话语言指定并没有给各角色绑定声线；实际三段均无音频参考。角色声线仍未绑定，不能把“同一声线”的文字描述算成真实声音身份。
6. 旧静态资产清单的`actual_selected_images=[]`、`identity_and_costume_definition_status=pending_aesthetic_samples_and_user_choice`。后续复用了获批视频画面，但没有将其登记成逐角色的可复用身份档案。这是原本待补的制作环节。
7. 十项文本审查核查剧情、来源、时序、闭合人数及机位，没有“共用角色身份档案完整”“每段身份属性投影覆盖”“原尾帧是否能辨认下一位主体”的放行条件。文档SCRIPT_VIDEO_RUN.md已有角色重新入画须保持可辨身份的原则，但当前单尾帧入口只验文件来源/批准/哈希，未落为可核验的角色可见性证据。最新审查全部pass并不证明人物外观正确。

服务内部为什么改变性别或错配人物，单靠请求和用户反馈不能证明。原尾帧是否只清楚保留某一个人，也是未观察的事实，不能猜测。不过上述合同缺口已能定位，不应继续只补“别换人”的提示词后重试。

## 最小流程修改方向

建立一份独立冻结的`SHARED_PRODUCTION_MANIFEST`，固定源/制作序列、人物身份、场景道具规格、人物与批准原始资产的映射及参考使用方式。所有属性附来源和known/unknown，不能根据名字或未看的像素补值。所有段依赖同一manifest版本与SHA，导演和表演模型不得逐段改写这些身份。

每段输入由四部分组成：同一共用制作设定、紧邻批准原尾帧与当前状态、本段源事件与对白、本段模型提交的完整表演。编译器机械投影共用人物与场景信息，输出属性覆盖表；DeepSeek审核完整新演法与共用设定是否冲突。本地在任何视频请求前检验角色一一映射、关键属性完整、参考来源/哈希、同一manifest绑定、状态前提及实际请求覆盖。当前缺失项先补一次，不靠各段模型重新猜。

单首帧路线还必须有“下一段主体能从上一段尾帧辨认”的证据。缺失时先修分镜/尾态安排，或另行验证适合身份与状态参考并存的生成路线；不能直接把额外素材塞进现有first_frame模式。模型模式及官方许可需另做当前核验，此次不承诺已适配新模式，也不擅自切换模型。

真实视频身份、位置、声线和表演继续由用户审核。共用设定和投影通过，只证明制作输入完整，不证明生成一定遵守。
