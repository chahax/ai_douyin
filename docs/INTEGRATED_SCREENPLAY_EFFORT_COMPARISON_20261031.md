# 《渡口》式完整剧本单节点：MiniMax 四档一轮对照

用户要求：调整为对白、动作、神情交织的完整剧本，再用不同强度 MiniMax 测一轮。

结论：四档都得到完整原生稿，均 needs_revision。新入口不再由声音抽取逐字合同阻断整稿，但背景与目标范围仍有语义错误；不是全书或无人生产验收通过。原始候选没有手改，没有迁移生产默认、生成媒体或发布。

## 实际修改

- 新模块 `src/content_factory/novel_adaptation/integrated_screenplay.py`：一个作者节点生成必要背景、完整场景与待核事项；对白、动作、神情和反应按同一场景交织。取消独立声音清单与音频ID依赖，不做固定秒数分段。
- 新入口 `scripts/run_integrated_effort_trial.py`：同源、同提示、同输出上限，medium/high/xhigh/max各生成一次；每份用固定max独立审核一次。原文证据、原始流、累计用量和未知不重派机制复用。
- 对白尽量保留，叙述允许转换可见动作；协议仅验证非空完整文本。协议通过不是内容通过。用户已接受的“融创乐园附近便利店”作为单独 production_choices 实际进入每次请求，不冒充原文方位。
- 沿用《渡口》的组织方式，不发送它的人名、剧情或旧稿作为仿写内容；未带旧声音321、旧审核或旧错误清单给作者。

## 思考强度的关键限制

已核对原生REQUEST，reasoning_effort四档都实际设置，adaptive与32768上限一致。官方当前OpenAI兼容文档支持该用法：

https://platform.minimax.io/docs/api-reference/text-openai-api

但high/xhigh/max作者调用332/334/336，以及xhigh候选的max审核335，原生usage均报告reasoning_tokens=0；逐条CHUNKS也没有reasoning_content，content无think标签。worker原样记录流并累积reasoning字段，因此不是仅阅读版漏展示。medium作者与另三次审核有真实非零推理返回。

当前只能证明“请求不同强度并取得这些候选”，不能证明四次实际思考深度递增，更不能从本轮断言高档普遍劣于medium。服务端实际行为、兼容协议影响等原因尚未确认，不擅自认定参数无效或服务造假。本轮8次边界已完成，没有追加接口试调用或重跑。

## 共同改善与剩余问题

四份稿都能读成自然场景正文；到站后牵手、系统提示后转头对视与笑容均保留。四份正文便利店都按已接受地点处理，但xhigh背景又增加商圈便利店，不能因正文正确就说整个设定通过。

跨档并没有稳定赢家。medium与max删除了歧义对白，不能把“无错误署名”当成功；xhigh正文保留未署名，待核说明却又猜了说话人。高档的背景说明仍会自由补排行、知情、母亲生死等信息。max把前情写成正文说明仅靠chapter.role提示没有可靠约束范围，xhigh则反向把目标开头当作前情概述。

下一步建议保持一个完整剧本作者节点，但先核实接口的推理返回；在输入构造层将目标正文与前情明确分栏，固定目标起止与必要事件覆盖核查；背景仅提取当前必要且有证据的内容，避免生成全排行和无关生平。这是后续方向，本次未另跑第二轮。
