# 自动文本主链的目标与根因记录（2026-10-11）

## 当前目标

用户本次明确要求：定位内容问题，分析原因，核对流程为什么产生该问题，修改流程，再从新流程完整生成一份剧本。目标是后续文本主链脱离逐稿人工监管，不能继续依赖用户指出每一句的问题后，由助手追加专项返修约束。

这一要求取代“每份候选交给用户挑错后继续局部返修”的推进方向。用户仍可提供选题、审美与新反馈，但运行时不能把缺少用户逐稿确认当作正常文本质量机制。新合同的机器文本验收不代表用户实际采用，不得写入人工 approved，也不证明无人监管质量已经可靠。

既有任务、原稿、模型回执、审查结论、冻结源码、账本与人工反馈保留，不静默迁移或回改。视频仍按 AGENTS.md 由用户人工审核；本次文本自动化不授权视频、抽帧、听看、ASR、音画审核或发布，也不扩大其他批次的续段例外。

## 已验证的系统原因

### 1. 核心表达问题可被审查发现却不影响文本放行

当前 432 完整新稿和 433 同稿全文复审的证据在：

- `data/production_revisions/legal_ending_withdrawal_revision_20261011/round_03/REVIEWED_CANDIDATE/FULL_TEXT_REVIEW.json`
- `data/production_revisions/legal_ending_withdrawal_revision_20261011/round_03/INDEPENDENT_EDITORIAL_GATE.json`

433 明确写出 B4.S01“今天这个名我签不下来”的动词、主语关系略含混，仍将其列 suggestions，输出 issues=[] 和 human_spoken_language_feedback_addressed=true。独立门也记录施事关系含混、用户仍可能认为不自然，却给 text_candidate_qualified=true，并要求交付用户核对。

`run_legal_ending_revision_v14.py` 的 validate_captured、`run_legal_complete_revision_v11.py` 的 finish 以及 ending finalizer 的放行依据主要是 issues 是否为空、事实/反馈布尔值和同源独立门，没有逐项文本功能状态。结果是：审查回执完整，尚未证明关键表达直接听懂，仍可被交付为候选；用户承担了最后一次发现问题的责任。

这是验收合同缺口。并不表示所有 suggestions 都必须阻断；关键冲突的施事、对象或意图歧义与可选的措辞美化必须分别处理。

### 2. 专项结构选择逐稿增加，没有泛化为创作功能判断

- `run_legal_complete_revision_v11.py` 的 bound_dialogue_rounds 固定 B2 三句、B3 两句。
- `run_legal_ending_revision_v13.py` 的 fixed_beat_schema 固定原生 B1–B3，仅开放 B4；spoken_action 列出几种空泛结束语。
- v14 将 B4 限定恰好一次对白。
- v15 将 B4 限定对白、收纸、出门、呼气四项 steps。

这些选择已明确标为本次修订范围，不能当成所有故事的通用结构。它们能限制当前输出形状，却不独立检验新故事的行动目的、阻力、策略变化与收束结果。仅新增禁句或固定拍数，会继续要求助手逐稿决定哪里锁、几句、几个动作。

已验证的是当前入口依赖逐稿结构选择；尚未证明固定句数直接造成坏台词。

### 3. 完整返修基础存在，但文本语义决策仍有外置停点

`creative_full_script_revision.py` 已要求模型提交完整新版，允许调整整篇对白、动作和节拍；不从旧稿抽拍拼接，这是可复用基础。

`creative_workflow.py` 的 _review_script_before_directing 已有全文复审与整稿返修循环。然而 _verified_review 在缺少 assistant decision 文件时写 script_review_pending 并返回。专项返修另外依赖外置 INDEPENDENT_EDITORIAL_GATE，finish 最终写 complete_reviewed_text_awaiting_human_content_confirmation。

因此，已有自动阶段循环不等于运行时无需人工/助手逐项核实。专项脚本与通用主链的语义放行来源不同，自动决策产物尚未形成统一合同。

## 仍为推断、不能写成已证实的原因

- 固定拍数、固定句数和负面例句可能压缩人物表达、使模型写出符合形状但不自然的对白，需要新合同与不同故事的真实对比验证。
- 大量历史失败稿可能使生成模型继续模仿旧表达，需要核对实际请求并做隔离对比；不能仅凭版本数量下结论。
- MiniMax 的能力不足、模型不能识别全部规则，或长分析耗尽输出的服务端原因，均不能由当前台词质量或短任务成功反推。
- 单次 DeepSeek 与独立门都放行不证明标准已可靠；离线模拟不证明真实创作质量、观众感受或视频质量。

## 最小可复用修改

1. 版本化新文本功能合同。事实、人物关系、资源与用户硬约束保持冻结；拍数、句数和具体对白不沿用本次病例限制。
2. 对六类核心文本功能逐项输出 pass/fail/unknown、当前正文引用、功能说明及可定位问题。核心施事/意图歧义不能靠 issues=[] 或 feedback_addressed=true 放行。引用路径必须指向当前稿真实叶子；遗漏和 unknown 不能通过。
3. 结尾判断最后一次交涉造成的当前结果是否在实际对白或动作中兑现。只离场没有结果不能通过；动作已经兑现结果时允许没有结尾对白，不强加解释句或金句。
4. 单一状态机调度完整生成、确定性编译、全文审查和有据内容返修。内容失败消费明确新问题，再由模型完整提交新稿、再全文复审；不手工补正文，不需要人工 decision 文件。质量仍不足时记录停止原因，不能伪造通过。
5. 保留请求身份、冻结输入、原生回执和累计消耗。重启复用已派发记录，服务结果未知先对账原请求，禁止重复派发；不重置旧 433 次、6,803,210 reported tokens 和 93,117 未知用量预留的承接基线。
6. 先离线验证三种题材及不同拍数的合同和自动状态循环，再独立真实试跑。题材夹具只是合同反例，不是人工质量金标，不引入商品性能或法律结论的推荐。

## 验证边界与实施分工

本文件记录只读审计得到的原因及已授权的流程修改方向；当前尚未凭本文件宣称自动文本主链已通过。新合同模块为 `creative_autonomous_text_contract_v1.py`，新运行入口为 `run_autonomous_text_pipeline_v1.py`，离线验证为 `test_creative_autonomous_text_pipeline_v1.py`。这些为独立版本，历史入口与冻结记录不改。

## 首次真实自动试跑：阶段成功，但质量门假阳性

新 v1 入口实际完成 434 场景规划、435 完整剧本、436 同稿全文审查，三次调用 20,478 reported tokens，累计 436 次、6,823,688 reported tokens；原 93,117 未知用量预留保留。无需人工 decision 文件，完整六拍正文和审查已保存，机器状态为 text_ready_for_director。

此状态证明了自动阶段和技术保存执行；独立核对发现文本门漏项，不能解释为可采用的剧本或自动创作质量通过。独立记录：`data/production_trials/autonomous_text_pipeline_20261011/legal_resignation_01/FAILURE_ANALYSIS.json`。本记录不改原 state、原生正文、审查、自动决定或账本，不生成替代它们的人工批准/驳回文件。

已确定的实际遗漏：

1. 初态是申请面朝上放在周姐面前、笔在旁；B1 第一条实际动作却从文件夹里取出申请，并由面朝下翻朝上。factual_physical 仍 pass，没有逐项起态对照。
2. B1.event 摘要说先通知再递纸，但实际 steps 是先递纸、后说公司决定。摘要不能补正文先后；本次确认的第一次通知和递纸关系未按实际演出核对。
3. F3 要求公司诉求遭拒后才转私人请求，再遭拒。B2 两句是质问/追问，正文直到私人请求后的 B4 才明确说不能签。review 整体却称“两次拒绝”，其逐句解读也只把 B2 两句解读为质问和追问，未支持总体结论。质问可以表现反对，但不能无证据地当作第一次明确拒签已经演出。
4. 两处把“体谅”写成“体量”。review 已发现，却说可能有意口语、不影响本轮判定；对应对白仍被解读为 conversational。这是字面理解与判定覆盖之间的缺口，不能由人工直接替换字形解决。

六条整体标准的覆盖不等于每项事实、起态和字面含义都已覆盖。计划中的“两次拒绝”及摘要中的顺序还会影响审查判断；这里能证明漏检，不能由此直接证明模型内部为何漏检。

下一最小流程改动应增加通用事实/起态逐项对照和独立字面重构审计。原 review pass、独立 audit fail 时程序自动触发完整返修，再检查全稿；不能把这次助手人工发现的问题记录当成长期自动验收机制。错字、未演出的第一次拒签、起态反转都要由模型提交完整新稿修复。新门仍需真实试跑，离线验证只证明 fail/unknown 不被覆盖。


## v2 的最小修复与最终离线验证

v2 在全文审查之外增加独立字面重构，逐项覆盖冻结的事实和人物/道具初态；实际 steps 的证据必须按原顺序覆盖，不能用计划或事件摘要补演出。两条检查都绑定同一整稿。审查 pass、字面审计 fail 时自动生成完整新稿，之后重新全文审查与字面审计，不需要助手或人工 decision 文件。错字被归为 language_error 后必须返修，可选风格建议与关键语言错误分开。

最终实际执行 `test_creative_autonomous_text_pipeline_v2.py`：48 项通过，独立复跑 12.23 秒；主任务另一次复跑 14.74 秒。详细断言和源码 SHA 在 `data/production_trials/autonomous_text_pipeline_20261011/legal_resignation_02/OFFLINE_VALIDATION.json`。未派发任何真实模型、媒体或发布请求。

真实入口接模拟服务完成七个阶段：规划、首稿、全文审查、字面审计、完整返修稿、第二次全文审查、第二次字面审计。首稿审查 pass 而起态审计 fail，程序自动返修；第二原生完整稿从四拍改成三拍、拍 ID 全换，交付正文与原生第二稿确定性编译一致。审计只接 brief、当前正文与证据目录，不接计划、参考分析或先前审查结论；创作和全文审查仍接参考全文，元数据按实际记录。完成重启无额外派发。模拟承接 436 次、6,823,688 reported tokens、93,117 未知预留，七次 mock 后 443 次、6,824,388 reported tokens，父账本字节不变；这些 mock 消耗不写入真实账本。

加固父授权/冻结快照/回执身份检查后，早先 37 项夹具出现 10 项失败，因为 mock 缺少真实 AUTH 和冻结源；补齐夹具而未放宽门。随后暴露并修复新 v2 运行器的 Windows 实际缺陷：`glob('call_*.json')` 大小写不敏感，错误纳入 `CALL_LEDGER.json`；现按 casefold 排除账本，正常父绑定通过，负数 token、错序号、重复/孤立回执和授权/快照篡改仍阻断。历史 v1 入口、回执和自动状态未改。

离线通过仍不能证明模型会真实识别第一次拒签缺失或顺序错误。下一步应先对真实 v1 失败正文做盲字面审计，本地预期问题不送模型；若真实门漏检，停止新稿生成并继续修流程。即使随后获得 text_ready_for_director，也只能报告机器文本验收，不写人工 approved，也不证明创作或视频质量。


## v2 真实盲测：引用完整，事件逻辑仍未强制

437 号 DeepSeek 独立字面审计成功返回 22 条实际步骤、6 项事实、5 个起态对照，消耗 8,845 reported tokens；累计 437 次、6,832,533 reported tokens、93,117 未知预留。它发现申请初态不符，却未发现 F3 第一次拒签缺失。本地盲测门按预期问题阻断为 halt_gate_regression_failed，没有派发新稿或视频。实际证据见 legal_resignation_02/FAILURE_ANALYSIS.json；原状态和所有冻结记录保留。

同一审计逐句把 E0004/E0006 还原为 question，把 E0008/E0010 还原为私人 request，把 E0012 还原为 refusal，却在 F3 的总体行判 pass，F5 还称 E0012 是“第二次明确拒绝”。问题已不是缺引用，而是程序仍把总体 pass 当作权威，没有依据逐句功能和先后关系复核事实逻辑。带否定的质问不自动成为已执行的拒签；私人请求后的同轮两句也不能补出私人请求前缺失的第一次拒签。

起态 fail 的修复建议还提出改变或删除冻结初态，实际没有执行；应要求修生成正文遵守源事实，不能为保留生成动作而改用户要求。字面 E0010 的“体量”也在审计 actual_action 中被直接归一成“体谅”，因此字面概述本身不能代替语言完整性复审。该探针未执行新稿全文审查，不能说新 language_integrity 项已经真实失败。

下一个可复用门应从已确认事实派生原子事件义务及顺序关系，将每项义务绑定实际步骤的角色和言语功能；不同交涉事件不能复用同一条引用冒充两次发生。若总体判 pass 与实际事件关系矛盾，机器应自动形成整稿返修要求。这个方向仍要离线和独立真实探针验证，不能把 48 项离线通过升级为真实判断准确。


## v3：源事件与实际事件的确定性核对

v3 的新计划把事实展开为 source_obligations 与必要 source_order；独立字面审计把义务映射到实际步骤。程序再检查真实施事、事件/言语功能、明确的不同发生与严格先后。因此事实总体 pass 与本身字面 question/refusal 的矛盾会派生完整返修，而不需助手再交一份人工决定。同一句可以完成多个目的；只有源事实要求先后或不同发生时，才禁止共用同一个引用，不强加新句数。事实和起态的可执行修复目标固定为修完整正文遵守冻结源，保留审查原生错误建议作为证据。

最终离线命令 `test_creative_autonomous_text_pipeline_v3.py`：39 项通过，8.46 秒，真实模型/媒体/发布调用 0。实际入口模拟自动完成七阶段完整两稿、两次全文审查与两次字面审计；第二原生完整稿改为三拍和新拍 ID，没有人工 decision 或正文拼接。继承 437 次、6,832,533 reported tokens、93,117 未知预留，mock 后 444 次、6,833,233 reported tokens，父账本不改。细节和源码 SHA 在 legal_resignation_03/OFFLINE_VALIDATION.json。

仍有明确边界：计划从自然语言提取源义务本身由模型完成，逐 fact 有覆盖不保证一个复合事实中的所有原子事件与先后都被提取；字面还原的语义和 state/absence 判定也不是本地可直接证明的事实。v3 强制的是已提取义务与已还原实际事件之间的可计算一致性。须再真实盲测后报告源门效果，不能用这 39 项离线通过替代模型判断准确或自然剧本质量。
