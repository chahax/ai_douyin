# 新来源参数化文本会话开发方案

## 问题与证据

历史602至619的18次调用没有增加完整正文。旧v27只允许复用618，绑定过期机会和619消耗；620新增消耗已由独立只读模块完整承接。12条历史分类测试验证了法律路由，不证明175字段完整源审查、新来源热度或创作质量。

新生产须接新真实来源，不能把618的来源换掉。冻结旧入口不修改。开发一个参数化会话对象，显式接收root、来源目录、当前修复轮key及620锚点，替代继续复制硬编码ROOT的入口。原参考全文和表达标准沿用，人物方向仍是用户确认的超市老员工与有调任压力的经理，强化当场情绪交锋，结尾保留明天的班。不得夹带旧618正文、旧审查报告或修订模板。

## 分工和合同

复用creative_goal_context_workflow_v23的纯prepare/validate函数、实际SDK出站和回执、TaskStore、同稿semantic/physical复审和确定性正文编译。新小型runtime仅解除v11的“只能reuse618”专项限制，保留source6精确服务Schema、模型/参数、原始证据、预算和未知停止。规划与setup共用goal_plan计数；首轮最多1份完整规划和2份setup，source/commitment/drama各1次，正文初稿加2份完整修订，同稿全文每次最多2项复审；上界15次，最短成功8次。此为本次局部安全边界，用户MiniMax续行授权与累计消耗不重置。

新source bundle先验证全部实际回执、同批样本门、标签图谱和当前时间有效性，再经compact_context投影；完整本地元数据保留，最多6条代表性元数据不重算样本门。实际模型请求中必须核对R01全文一次、独立完整法律上下文一次、表达标准和已确认功能要求。user_goal_contract复用经过确认的功能行及两个超市方向行，不能引用旧INPUTS里的source_packet。

620 anchor只核历史完整性和用量，不能通过当前freshness。每次实际派发在锁内核新的来源门、当前计数轮、冻结源码/配置和620锚点。prepare不构造客户端，run独占claim，重复run/未决/截断/未知用量停止。结果完整已知但内容不合格按有界完整原生修订；不手改模型稿，不将机器通过写为用户采用。当前不增加媒体或发布，旧导演7/7保留。

## 实施边界

输入桥负责新bundle完整性、真实时间门、紧凑INPUTS与原用户方向映射；会话对象负责声明式路径、实际请求、阶段状态与完整文本交接；CLI仅prepare/run/status，不复制旧版本全局变量。先离线故障分支及真实预览主审，再登记新运行一次。规划结构或三审明确失败先保存证据并结束本次验证，在下一修复轮定位，不暗增规划次数。

当前第2轮仍负责实际来源恢复与620承接。来源采集完成并有明确结论后封存第2轮，第3轮才登记新会话开发与真实文本验证；本方案准备本身不另计轮，不把测试项或调用数当轮数。

## 验收

必须拒绝过期/别账号/别批/篡改来源、619漏620、未知/重复claim、旧轮key新派发和请求语境缺参考；未知运输与完整内容拒绝分流。完整原生正文与同稿双审得到后才可记text_ready_for_director；没有正文时如实报告停点。本次不承诺开源组合或Schema会自动保证情绪和画面质量。若新结果不满意，可恢复20261012和20261015独立基线，账本/回执不能回滚。
