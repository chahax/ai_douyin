# 小说转视频剧本：专用Agent与现实逻辑修复方案

日期：2026-10-17。状态：官方资料与本地实现已核实、方案已保存；尚未安装新框架、实现新运行器或进行新模型/媒体调用。

## 推荐与当前问题

推荐在现有项目中增加独立小说剧本工作流，采用LangGraph作为可选编排适配层，保留MiniMax创作、DeepSeek必要审查与项目原派发账本。领域核心先做“场记状态账”和“审核问题核实/去重”，不靠增加多个泛化审稿角色来替代具体检查。

当前v3已完成真实的原生完整稿→同源全文审核→有界整稿返修，但没有把现实场景按事件更新，也没有区分审查发现与已证实问题。三轮实测出现过度限制对白改编、同一问题跨维重复列项、返修只增加声明而不解决内容，以及动作连续性判断证据不足。开源框架解决步骤编排，能否降低漏检、误报和返修回归需要独立评估。

## 开源选择与证据

1. **LangGraph：优先的编排适配选择。** 官方提供显式状态图、条件分支、并行检查和生成—评估循环；检查点支持恢复，SQLite适合本地工作流。核心仓库MIT。参考[官方仓库](https://github.com/langchain-ai/langgraph)、[工作流模式](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[检查点](https://docs.langchain.com/oss/python/langgraph/checkpointers)。它可独立于LangChain使用，因此保留现有CreativeRoleClients，不另换模型客户端。以上是能力支持，不表示本项目已经接入。
2. **FilmAgent：借鉴场记协作方法。** 原仓库现重定向VideoClaw，FilmAgent在[历史独立目录](https://github.com/HITsz-TMG/VideoClaw/tree/main/FilmAgent)中，README明确两者不互相调用。可参考Critique–Correct–Verify、Debate–Judge与角色位置/动作/对白的联合检查，见[论文](https://arxiv.org/abs/2501.12909)。原实现依赖预建Unity空间，不能据此保证任意小说或生成式视频满足物理规律。历史README许可证徽章与当前VideoClaw根许可证归属不一致，本方案参考机制自行实现，暂不复制历史代码。
3. **CrewAI Flows：备选。** 官方有结构化状态、listen/router、SQLite持久化，见[官方文档](https://docs.crewai.com/en/concepts/flows)。目前项目已有状态与账本基础；本方案更需要显式状态转移和精确问题路由，优先选择LangGraph适配，不同时引入两套框架。
4. **MovieAgent：后续导演分镜参考。** [官方执行代码](https://github.com/showlab/MovieAgent/blob/main/movie_agent/run.py)有编剧、场景与镜头规划，但独立script supervisor初始化被注释；不能直接当成本项目所需的逻辑纠错闭环。代码复用许可尚未确认。
5. **Story2Board：后续视觉预演参考。** [官方仓库](https://github.com/DavidDinkevich/Story2Board)侧重分镜图一致性，不能替代文本因果审查。代码MIT与所用模型权重许可分别核对，首期不安装视觉生成依赖。

本地实查：Python 3.14.3，pydantic 2.13.4，openai 2.37.0；未安装langgraph、langgraph-checkpoint-sqlite或crewai。新增依赖须在独立环境锁版本并验证，不能以官网支持等同本地兼容验收。

## 最小工作流与职责

```text
已取得的小说正文、目标时长与改编范围
  → 冻结来源、人物关系、关键事件与允许改编边界
  → MiniMax：背景/选角/主线高潮/改编规划/完整原生剧本
  → 场记：区分叙述层，提取事件及人物/道具/知情状态
  → DeepSeek：对照全文进行连续性、因果、人物与可拍性审核
  → 问题核实、反证与合并
      有确证重大内容问题 → MiniMax完整新稿 → 同稿全文重审
      仅轻微建议且完整审核通过 → 文本导演交接
      证据不够、技术结果未知或容量耗尽 → 保存明确停点
  → 后续导演：场景拆分、动作/对白/反应窗口与段首段尾
  → 视频执行仍按既有授权和用户人工审核
```

这些是逻辑职责，不等于每轮都调用五六次模型。首版可把场记抽取与全文逻辑审查合为一次DeepSeek响应；若上下文或实测效果需要再拆分。问题核实先做程序去重和规则检查，仅对影响放行且存在争议的major请求一次必要的独立复核，模型和次数在新运行冻结时明确。创作/返修按版本串行；互不依赖的审核可并行，但都必须绑定同一完整稿和来源。

MiniMax继续交原生Markdown/纯文本。场记和审核作为旁侧产物，不要求编剧复写JSON、调用规定工具或逐字匹配小说引用。程序分配文档/场景/段落身份，模型不猜hash；证据用于解释问题，排版差异不作为创作失败。

## 现实逻辑检查的方法

每场维护时间线（现在/前世/回忆/设想）、在场人物、相对位置、姿态、手与道具、人物已知信息、事件起止状态。每个事件注明前置条件、可见动作及后置结果，并连接前后事件。

必须同时记录：

- 叙述层：背景分析、段首状态/概述、正式表演、段尾摘要；同一动作可以在不同层被重述。
- 事件同一性：same_event、continuation、new_event或ambiguous，不能把重复文字直接算重复事件。
- 解释状态：known、inferred、ambiguous、unknown；模型抽取不冒充绝对世界事实。
- 来源层：原文明示、合理表演设计、压缩/合并、实质新增事实。只有实际改变主线或造成矛盾时才升级严重程度。
- 稿件位置与上下文：由程序绑定本次稿件，不要求引用照搬空行/标点。

确定性程序可检查已确认状态之间的矛盾、未解释的道具/人物转移和重复问题。对于未知、比喻、省略、共同行动、回忆或叙述层不明，返回待消歧，不自动补全世界状态后再用猜测拒稿。小说存在重生等设定时，按其世界规则检查内部一致性，不用日常物理规则拒绝已明确设定。

修复目标应描述内容结果，例如“将两处表述明确为同一次持续拖拽；或补出落地/再次拉起的原因”，而非锁定固定句数。MiniMax提交完整新稿，复审重新覆盖全文，确认原问题解决且没有引入新问题。

## 审核问题核实与去重

每条问题至少包含涉及事件、具体上下文、违反的明确条件、合理解释/反证、对观众理解或可拍性的实际影响、严重程度、结论（成立/建议/不成立/不确定）及关联维度。

同一根因跨人物、对白、因果等维度出现时，只保存一条问题并关联多个维度。相似词不等于同一根因；相同词也不能自动归为人物身份错误。提出重大问题必须说明为什么不是允许的改编、持续动作、场景摘要或合理省略。

不确定问题不伪装已通过，也不自动消耗编剧整稿返修。已完整、用量已知的审核可在冻结范围内做有界核实；运输未知、截断、用量未知与不完整技术产物继续停止，不由仲裁员猜测补成通过。仲裁有权驳回错误审查结论，但无权改写原文或为通过迁就事实。

## 对此前主审意见的补正

此前主agent把“段首揪领＋正文拖起”直接称为确定重复动作，证据不充分：二者可能是概述和同一动作展开，需要先核实叙述层与事件同一性。“最年幼却保护更小的孩子”也应先区分年龄与体型；原文没有“最年幼”属于新增描述，但是否重大应依据实际影响。不能把主审判断直接写成真值。

这项补正不改变DeepSeek原生三次revise、不追认旧稿通过、不改写任何旧响应、账单或冻结记录。后续评估将上述情况列入防误报样本。

## 仓库复用与建议模块

独立新增模块建议：

- `novel_scene_ledger_v4.py`：时间线、叙述层、事件/实体状态及unknown/ambiguous。
- `novel_logic_review_v4.py`：同源全文审查、问题影响与真实证据。
- `novel_issue_adjudication_v4.py`：问题归并、改编边界核实、必要的一次独立复核。
- `novel_agent_graph_v4.py`：领域流程与可选LangGraph适配。
- 新独立CLI及网页入口：准备、预览、执行、检查、阶段产物与核实结果展示。

复用v3的源冻结、原生请求/响应、用量、同源登记和同稿全文复审机制，使用独立适配，不修改已冻结v3文件。`creative_studio_task_store_v1.py`已有SQLite事务/唯一claim/revision/恢复，可作任务索引或底层实现来源；原服务调用账本保持唯一权威，不能让两个账本各自派发。

`creative_studio_reference_previs_v1.py`只用于后续具备明确米制几何与来源的白模。小说场记先用相对空间和未知状态，不能要求模型猜绝对坐标，再把猜测当资格门。角色/场景素材在导演准备时检索已有`personal_catalog_v1`，入库、选角和人工视频批准保持分开。

LangGraph检查点不等于外部请求只发生一次。其[官方Functional API说明](https://github.com/langchain-ai/docs/blob/main/src/oss/langgraph/functional-api.mdx)指出未完成任务在恢复时可能再次运行。因此所有节点调用现有admission与唯一claim：存在已保存原生响应则复用，已派发未知则停止/核对，不让图框架自动重发。关闭SDK和节点运输自动重试；回放或换thread_id不能重领创作容量。

## 回归样本与验收

先用已保存的原生小说/三稿/三审建立离线回放，并加入成对样本：

| 应检出的异常 | 应允许或需消歧的对照 |
|---|---|
| 明确两个独立起身事件，中间没有倒地 | 段首概述与正文展开同一事件 |
| 无转场或时间变化的人物瞬移 | 有明确省略/转场后的移动 |
| 唯一道具无转移便被另一人独占使用 | 已有交接、共同持有或道具并非唯一 |
| 明确缺席人物在现在现场接话 | 回忆/电话中的回应 |
| 人物使用明确不可能获知的信息 | 经他人告知或观众知道、人物未知的旁白 |
| 显式年龄最小却出现比他年纪更小的人 | “更小”指身材或含义不明 |
| 新增改变核心动机的前史 | 不改变因果的表情、走廊、普通动作 |
| 专属经历被误移给另一角色 | 多个人用相似骂词 |
| 返修引入新矛盾 | 对原问题有效修复且全文保持一致 |

分别报告真实错误检出率、合理改编误报率、未决问题比例、去重效果、返修后新问题和实际用量；不能只报告测试条数。保留不参与提示调试的故事/场景用于验证，避免只会修当前这一章。

完成标准分层：领域规则与恢复离线验证→真实模型完整新稿/同稿复审→可执行导演分段→用户视频人工审核。文本机器通过不等于实际视频逻辑正确或用户审美采用。

## 实施顺序与现有停点

第一阶段：实现场记及核实核心、成对测试、旧真实响应离线回放。第二阶段：独立环境验证LangGraph适配、原账本恢复及网页/CLI接线。第三阶段：新冻结与明确容量下实际生成、全文复审及导演脚本验收；最后才进入既有授权范围内的媒体制作。

当前同源小说历史20次/310301 reported tokens、原冻结调用容量剩0，旧响应、失败与上限完整保留。本次研究和方案保存没有新增模型、媒体或发布调用；设计新图或换目录不会解除原停止门。新生产测试需要记录新增范围与容量，承接历史后再派发。
