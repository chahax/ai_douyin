# 逐场调度与状态承接 v3

## 实现范围

独立 `story_first_contract_v3.py` 与 `story_first_production_v3.py`，CLI `run_story_first_production.py` 新 prepare 默认 v3，旧冻结 PLAN 仍用原版。账号后台、旧 corpus/Fanqie 网页未切换。

基础设定与完整剧情固定后，每次只生成一场调度。请求包含完整合成原文、基础设定、整集剧情、当前场、前一同时间线的结束状态和下一场信息。每场最多8动作、12状态变化、4进场、6音轨；文本字段最多240字符。Schema与程序均限制每场最多15秒。

场首与场尾显式记录位置、持物、知情槽位，变化绑定原文和动作。下一场必须精确承接同一时间线前态，场尾只能由明确变化得到。位置与进场须能在状态变化链中对应。CURRENT与回忆/计划时间线隔离；具体语义和时序仍须模型及助手核对，程序不能证明所有必要槽位均已抽出。

场次缓存只在本次执行内使用。输入键绑定原文、基础设定、整集剧情、当前场、前态；对应场硬伤要求强制返修。前态改变则下游失效，前态一致且无直接问题的场次复用原结果并留证。没有实现跨进程自动恢复或未知请求重派。

审核仍绑定完整候选SHA和可逆证据编号；状态索引以完整状态记录为证据单位，完整字段仍保留。硬伤先由另一个MiniMax调用核验为upheld/rejected/uncertain。只有upheld驱动返修；全部驳回或证据不足会停止等待独立解决，不能将驳回当作原候选自动通过。称谓、动作对白并行、整句音轨与关键短语的时间区别写入核验要求，实际效果须看真实测试。

## v4/v5修复与最终结果

v3实际12次/144100 reported tokens，六场完成，无length；但prop槽关联人被错误要求参与动作，审核载荷超过容量门。v4修复prop关联人与动作执行者区分，知识/位置主体仍须绑定参与动作；记录级证据索引保留原稿全部字段，同一v3候选请求保守界88827/131072。前四场经SHA、原生返回与新校验验证后采纳，不改旧记录。

v4实际10次/137259 tokens：完成交叉审及独立硬伤核验，识别第三天/次日、道具结尾缺动作，退回基础设定并重建；后场新人物需要新增状态槽位，模型抄写前态又改变槽位集合，终止为state_registry_changed。

v5不再要求模型生成场首/场尾表，输出introductions和动作绑定的changes；程序保存原生delta并计算派生状态，不手改模型内容。既有槽位不得重命名或覆盖，新出现的人物/道具可显式引入；新增字段语义仍须来源审查。基础和剧情及第一场从v4原生结果验证采纳，新派发最多10次，与此前22次合计本轮32次工程上界，未重领旧任务预算。

v5实际10次/160133 tokens，全场生成、交叉审与核验已运行，准备下一轮返修时call_limit停止，pending=null。主助手needs_revision：过去事件画面与当下回忆者意识状态混用，审查把两个时间线当同一时点的理由不成立，开场和回忆仍偏慢。没有通过完整稿，DeepSeek尚未调用。首次完整产物为60秒规划，非成片实测。

最终144项新旧回归通过。本轮合计32次MiniMax、441492 reported tokens，Qwen/DeepSeek/媒体/发布0；v1/v2旧76文件SHA保持。三次失败全部保留不可重跑，原生响应与派生状态明确分列。验收见data/qa/story_scene_v3_20261026/ACCEPTANCE.json与data/corpus_production_trials/20261026_story_scene_v5/PRIMARY_REVIEW.json。

独立CLI新prepare默认v5，执行旧PLAN仍按原版本；账号后台及旧网页未升级。后续需分别表示历史人物状态、当下回忆者与音轨时点，审核按各自时间线判断；本轮未完成这项语义修复，不称Skill已解决内容质量。
