# 前端展示与运营管理改版评估

评估日期：2026-09-14，北京时间（UTC+8）。本次仅调查并出报告，未实施页面改版。

## 一、结论

前端需要修改，优先改信息组织、管理入口与数据关联，再优化视觉。现有后端已经有抖音绑定、登录健康检查、视频任务统计和火山引擎余额查询，主要问题是入口分散、配置抢占首屏，以及生成记录没有清楚关联到审核与成片。

建议沿用当前 Streamlit 和已有服务，先交付可用的管理界面。暂时没有足够依据支持整站更换技术栈。

本次证据来自路由、页面与服务代码检查，以及本地台账和余额接口实测。新建浏览器会话访问站点时停在登录页，未进入登录后的页面；因此内部页面布局结论依据渲染代码顺序，尚未完成登录后的视觉和交互验收。

| 优先级 | 当前问题 | 对使用的影响 | 建议 |

| P0 | 视频用量先显示渠道示意图、配置、默认模型和参数 | 第一眼无法回答用了多少、剩多少、哪些任务有问题 | 改为“视频用量与余额”，统计卡和异常提示置顶 |
| P0 | 余额按钮在渠道说明下，点击后才出现卡片 | 已接接口看起来像没有功能 | 固定余额卡，显示最近成功快照、查询时间和刷新入口 |
| P0 | 首页与制作页只扫描一层 production.json | 新逐段项目和独立 assembly.json 成片可能看不到 | 建立统一项目索引，关联剧本、片段、成片和审核 |
| P0 | API 成功与质量通过没有并列区分 | “成功很多、失败为零”与用户看到的多次审核不通过矛盾 | 分开显示接口状态、质量审核状态、成片状态、发布状态 |

| P1 | “用户管理”和运营账号概念混淆 | 不清楚管理的是后台登录用户还是抖音身份 | 明确命名“后台用户与权限”，与“抖音账号”分离 |

### 余额页面的具体缺陷

当前查询结果只保存在当前会话；查询失败会移除上一份成功结果。建议保留最近成功快照并显示“已过期 / 本次刷新失败”，避免余额突然消失。未配置、缺 SDK、无权限、网络失败、正在查询和真实零余额必须分开。

另有一个具体状态缺口：凭证齐全但 SDK 不可用时，按钮会禁用，却缺少明确的 SDK 缺失说明。

方舟账户余额、即梦 CLI 积分、BytePlus 本地预算不是同一种数据，必须按渠道分开，不能合成一个没有依据的“总余额”。管理 AK/SK 与推理 API Key 也应明确区分；页面只显示配置状态，不展示密钥。

## 四、建议的信息架构

主导航按工作顺序设置：

1. **工作台**：当前抖音账号、进行中项目、待审核片段、最新成片、余额提示、任务异常。
2. **抖音账号**：绑定身份、登录健康、浏览器环境、重新登录、账号切换。
3. **选题与剧本**：来源样本、音视频分析、账号策略、剧本版本与审核结果。
4. **视频制作**：逐段生成、审核证据、首尾帧衔接、重试计数、合成与最终检查。
5. **作品与发布**：成片、标题标签、封面、声明、上传与发布状态、平台回执。
6. **用量与余额**：渠道余额、实际账单、生成用量、项目成本、失败与重试。

数据复盘、任务中心作为辅助入口；知识库、技能、工作流、抓取、规则和模型配置集中到高级工具/系统设置。页面保留现有深色品牌风格也可以，重点是信息层级。

## 五、抖音账号管理应该有什么

| 能力 | 现状与处理方式 |
| --- | --- |
| 账号列表 | 汇总现有绑定：头像、昵称、平台身份、状态、最近验证时间、当前操作标记 |
| 登录与绑定 | 复用现有扫码/浏览器绑定及配置后的 OAuth 能力，移到独立入口 |
| 健康检查 | 复用现有健康、过期、不匹配、安全验证状态，并给出对应操作 |
| 浏览器环境 | 显示绑定的环境和验证来源；Codex 浏览器已登录不等于项目绑定已验证 |
| 账号策略 | 复用现有版本机制，作为账号详情页的内容策略标签，不与登录绑定表单混排 |
| 数据隔离 | 项目、作品、发布任务明确归属账号；全局切换后显示清楚作用范围 |
| 权限 | 区分内容编辑、账号绑定管理、发布、费用查看、系统配置 |
| 操作记录 | 记录绑定、重新验证、账号切换与发布操作，保留明确时间和结果 |

作品库当前引导用户去编辑者页面创建账号，而实际绑定又要求管理员。应按权限显示可执行操作或管理员协助提示，避免把用户引向无法完成的入口。

## 六、“视频用量与余额”首屏建议

```text
视频用量与余额                渠道 / 日期范围 / 刷新
当前费用账户与币种            最近同步：北京时间……

[可用余额] [本期实际费用/未接账单] [生成次数与秒数] [审核通过与重试]

异常：本地未决任务 / 同步失败 / 余额快照过期

项目用量 | 生成明细 | 账单明细 | 模型分布 | 渠道配置
```

配置、默认分辨率、默认画幅、模型目录移到“渠道配置”，保留需要时查看的入口。余额卡持续占位，不能未查询就不存在。

生成明细至少展示：项目、剧本版本、片段、尝试序号、实际模型、分辨率、生成秒数、接口状态、质量审核状态、任务 ID、tokens、费用来源与更新时间。默认按所选日期筛选，避免本月卡片与全历史表格口径不一致。

费用分开显示“官方已出账”“估算”“待同步”；没有账单时显示未获取，不显示 0。API 成功但审核失败的片段仍可能产生费用。

## 七、数据管理必须一起升级

建议统一关联：**抖音账号 → 内容项目 → 剧本版本 → 片段 → 生成尝试 → 审核 → 成片 → 发布记录**。费用按生成尝试关联，并以渠道与任务 ID 去重；不同重试不能被误去重。

不能只把浅层 glob 改成递归扫描：那会把重试目录、旧稿和准备目录全部当成项目。索引需要把同一项目的多次尝试归组，兼容 production.json 和 assembly.json 等已有材料。

统计口径必须独立：

- 接口成功数：供应商成功生成，不代表审核通过。
- 审核失败数：画面、连续性、声音等不合格，与接口失败分开。
- 本稿失败计数：新稿从 0 开始，同稿累计；历史另列。
- 可用成片数与时长：完整审核通过的最终版本，不能用所有片段生成秒数代替。
- 发布状态：待上传、上传中、已上传、提交结果待确认、平台审核中、已发布、失败。

提交结果不明时先查平台回执，不能自动重复发布。“已上传”也不能显示成“已发布”。此前两条视频尚无本次可确认的发布回执，应保持待核实。

所有时间统一显示 UTC+8，分别标明来源发布时间、获取时间、分析时间、生成时间、审核时间、账单时间与余额查询时间；不得用文件修改时间推断任务完成。

## 八、实施顺序与验收

**第一阶段：能找到、能看懂。** 独立账号入口；余额与核心用量首屏；修正文案；展示最新项目；拆分接口与审核状态。

**第二阶段：能管理、能追溯。** 统一项目索引、生成尝试台账、账号范围、费用关联、发布回执、角色权限。

**第三阶段：视觉与体验。** 统一卡片、表格和状态颜色；降低装饰占比；补齐加载、空数据、错误、过期状态；完成登录后的桌面和窄屏验收。

验收标准：

1. 登录后两次点击以内找到抖音账号身份、登录状态和重新验证入口。
2. 用量页首屏能看到余额快照及时间，查不到时能看懂原因。
3. 58 次 API 成功不会被理解为 58 条合格成片；质量失败独立可查。
4. 最新房东成片约 47.552 秒能在对应项目中找到，不与重试片段并列冒充多个项目。
5. 每次生成可追溯剧本、片段、模型、审核结论与费用来源。
6. 缺失费用不显示零；缺少审核不显示通过；没有平台回执不显示发布成功。
