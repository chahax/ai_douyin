# 自动剧本流程调试

修复可复现的流程原因，交付原生生成、可追溯的验收结果。Skill 是调试操作规范，不是已经实现的逐场生成引擎，也不自动运行定时任务。

## 先确认实际实现

在当前项目读取 AGENTS.md、相关入口、最近任务的 PLAN/STATE/RESULT 和原生请求响应，确定真实路线、模型、实现版本及任务是否结束。不要把历史文档里的“拟实现”当代码功能。项目线索及本 Skill 创建时的状态见 [项目接入](references/project.md)。

区分四类结果：程序测试、模型格式/来源校验、语义内容验收、成片验收。分别报告，不能相互替代。

## 定位与修改

1. 从失败原请求、原生终态和具体输出复现问题；先区别代码合同错误、容量/截断、内容错误和审核误判。检查原文与实际字段，不仅看错误摘要。
2. 按 [难点排查与验收](references/debugging.md) 选择需要的修复。固定上游事实和剧情后，缩小调度生成与返修单位；每次仍带足够的跨场上下文，不盲目切碎章节。
3. 修改流程、Schema、提示词和相关校验，保持要求一致。需要维护旧冻结任务时新增版本，不修改原任务来伪装重跑成功。
4. 对当前真实缺陷补充有区分能力的回归：正常合理情况应通过，真实矛盾应被拦截。只测试字段存在或模拟返回 pass 不足以证明修复。
5. 用户授权真实测试时，使用已授权来源和服务创建新测试任务，保存请求、响应、候选、用量与失败。旧 ended/unknown 任务不盲目重放；旧外发拒绝不会因调用 Skill 而解除。
6. 检查自动返修是否修到了问题、有无新增错误；最终审核绑定同一完整候选。助手独立审查原文、状态链与审核理由，原始模型稿和原审核结果保持不动。

若真实测试失败，定位本轮新证据支持的原因，在授权范围内继续有针对性的修复。达到该任务已批准的调用/返修边界，或出现未知调用时，保留记录并说明准确阻塞；不能另建任务绕过同一预算或审批。不要用手改稿替代流程验收。

## 交付

简述修改了什么、具体测试结果、真实用了哪些模型与来源、仍有哪些问题。提供完整候选和审查记录链接；候选未通过时明确标注。更新项目的现状记录，把未完成项列清楚。

Skill 本身不授予真实小说外发、媒体生成、发布、重启服务或新增调用额度的权限；沿用当前对话与项目已有授权，不重复询问已明确授权的同范围动作。
